# Cápárium nAPPló

Browser-based measurement log for the Budapest Zoo Cápárium: daily and weekly water measurements,
later feeding logs. Tablet first (iPadOS Safari), desktop browsers too.

The business rules come from the project documents (requirements v2, logical data model v1,
decision log). Requirement IDs (ÁLT-xx, VIZ-xx, …) and data-model rules (K1–K9, R-xx, T-xx) are
referenced in the code where a rule is implemented.

## Technical decisions

- **Next.js 16 (App Router) + TypeScript**, server-rendered pages, JSON API routes for the grid.
  One deployable, no separate API service.
- **PostgreSQL + Prisma 6.** Rules Prisma cannot express are in the migration SQL: one valid value per
  grid cell (partial unique index, T-02) and an append-only audit table (triggers reject
  UPDATE/DELETE/TRUNCATE, K6).
- **Two database roles.** Migrations and the seed run as the table owner; the server connects as
  `caparium_app`, which owns nothing, has no DELETE on journal data and only INSERT/SELECT on the
  audit table, so it cannot switch the audit triggers off either (K6 at the storage level).
- **Own session login** (scrypt password hash, random token in an httpOnly SameSite=Lax cookie, only its
  hash in the database, same-origin check on every write). No external identity provider.
- **Optimistic concurrency** (version per record), **idempotent writes** (client request id), and a
  **local retry queue** in the browser for short network drops (ÁLT-03, ÁLT-15). No silent overwrite.
- **Exact decimals** (Decimal columns, string arithmetic in the app; K8). Business day in
  Europe/Budapest with the midnight boundary (K2); late saves after midnight follow K9.
- **docker compose** (app + its own PostgreSQL). No database is shared with any other system.

## Run

```bash
cp .env.example .env      # set SERVICE_PASSWORD_POSTGRES; SERVICE_PASSWORD_SEED only in a test environment
docker compose up -d --build --wait app
# http://127.0.0.1:3000  (APP_BIND / APP_PORT in .env to change)
scripts/backup.sh ./backups                     # dump + restore check, copy of the dump
```

Start order inside the app container (`scripts/start.sh`): `prisma migrate deploy`, then the
synthetic test seed if `SEED_TEST_PASSWORD` is set (idempotent: adds what is missing, changes
nothing), then the server.

**Coolify:** a "Docker Compose" application on this file, without a domain (the app is then not on
the public proxy); `APP_BIND` = the host's tailnet address. `SERVICE_PASSWORD_POSTGRES` and
`SERVICE_PASSWORD_SEED` are generated by Coolify. Backups: a scheduled task on the `db` container
running `caparium-backup` (dump into the `db-backups` volume, restore check, keeps the newest 14).

Test users (password: `SERVICE_PASSWORD_SEED`): `teszt.admin` (adminisztrátor),
`teszt.akvarista1`, `teszt.akvarista2` (akvarista). All seed data is synthetic.

npm run build && SEED_TEST_PASSWORD=… npx playwright test           # needs a migrated, seeded DB

CI runs all of the above, the migration drift check, Playwright on WebKit (tablet 1024×768, touch)
and Chromium (desktop 1440×900), and a docker compose start with a backup restore check.

## Public test site

A Coolify domain (`https://<name>:3000` on the `app` service) publishes the app through Coolify's
HTTPS proxy. Then, before the first deploy: `BASIC_AUTH_USER` (the password is
`SERVICE_PASSWORD_BASICAUTH`, generated by Coolify) and `COOKIE_SECURE=true`. The gate
(`src/proxy.ts`) stands before every path: pages, `/api`, `/_next`; only the exact `/api/health`
(it answers `{ok}`) is open, for the container healthcheck. 20 wrong passwords from one address lock
that address for 15 minutes. The app's own login stays behind the gate, with its own lockout.

The gate fails closed: without its variables it is off only where nothing says the site is
public. Behind an HTTPS proxy (`X-Forwarded-Proto: https`) or with `COOKIE_SECURE=true`, a missing
gate answers 503 on every path but `/api/health`; running a public site without the gate needs an
explicit `BASIC_AUTH=off` with no `BASIC_AUTH_USER` (a password alone does not count: Coolify generates
`SERVICE_PASSWORD_BASICAUTH` for the compose even when no gate user is set; `off` together with a user is a
contradiction and answers 503) (passed to the container by `docker-compose.yml`, like every variable the
gate reads; `tests/unit/compose-env.test.ts` fails if one is left out). With a public domain, `APP_BIND` stays a private address (127.0.0.1 or
the tailnet): the limiter trusts the last `X-Forwarded-For` entry, which only the proxy may write.

## Before a production deployment

- `COOKIE_SECURE=true` is mandatory behind HTTPS (the test environment runs on plain HTTP on the tailnet).
- The login lockout (10 failures in 15 minutes) applies to existing login ids only, so the "locked"
  answer reveals that an id exists. Accepted for an internal staff app; revisit if it goes public.
- `SERVICE_PASSWORD_SEED` must be empty: no test users outside the test environment.

## Temporary settings (not final business rules)

- Reference ranges in the seed are **placeholder test values**; the admin sets the real ones.
- Pool groups follow the NY-03 default: "Nagy medencék" = Nagymedence, Kismedence, Karantén;
  "Kismedencék" = Korallos, Inkubátor, Ragadozós; Kis sózó and Sózó have no water measurement.
- Late-save grace period: 30 minutes (setting `late_save_grace_minutes`, K9); a client timestamp
  older than 48 hours is not trusted at all (`late_save_max_hours`).
- Trainee (NY-14 / T-06): no own login; "Gyakornok végezte" flag on the measurement.
- Animals, species, groups and feeds in the seed are **synthetic** ("Teszt Egy", "Teszt faj A",
  "Teszt hal"); the real list comes at go-live, with a separate approval.
- Coral feed doses (NY-04, EGY-09): the table exists, no dose and no conversion yet; waits for the
  customer's answer.
- One common daily feeding list for the whole Cápárium (NY-06 default): any aquarist may change it
  and finalize it on an open day (R-7).
- The feeding day closes automatically at local midnight (NY-05 default, T-01/3); an admin may close
  it by hand earlier. The automatic fasting days are born at the close, and only for a finalized list.
- Eating state colours (display only, DN-03): ate green, partly yellow, did not eat red, fasting
  light blue; in the eating Excel a day before arrival is light grey, after death or release dark.
- At most 5 "Egyéb" feeds per animal and day (the template's Egyéb 1–5, setting `egyéb_takarmány_max`).

## Status

- Part 1: login → pool group → record a daily measurement → saved → log with history.
- Part 2: weekly measurement (dilution 1–100 and RO/SW per cell, no recalculation), correction and
  invalidation with reasons (Figma 21), the day lock (automatic close at local midnight, admin reopen
  and close, a save made before midnight still counts within the grace period), pending late saves
  approved or rejected by an admin, settings for admins: reference ranges and pool names as a
  change or a correction (K3), users (create, role, deactivate, password, versioned monogram and
  ZIMS name).
- Part 3: Excel export (summary sheet and one sheet per system, the template's 8 columns plus
  dilution and RO/SW, red out-of-range values, old periods with their old names) and ZIMS CSV
  (one file per system, the sample's header, CRLF, quoted "Sep 20, 2026" dates, the customer's
  mapping letter by letter; a missing mapping stops the export instead of writing an empty field).
  Exporting is not submitting: an admin marks a run as submitted, and from then on every changed,
  invalidated or late measurement of the submitted period is listed as "leadás után eltér".
- Stage 2, master data: every animal an individual (also in a group), species, groups; arrival,
  transfer, group change, death and release as dated events, and the pool and group of any day follow
  from them, with the history kept (DAT-01, DAT-05, EVE-03, T-09). An arrival is admin work; an
  event on an earlier day needs a reason. The feed list by type, never deleted, only made inactive
  (DAT-02, TAK-07).
- Stage 2, feeding: the common daily list (a group selects its members of the day one by one), the
  list finalized, feeding items in pieces and grams that never add up (T-08, DN-16), a group item
  with a snapshot of who was selected (R-8), the same feed not twice to one animal (T-21). Eating
  statuses: ate, partly, did not eat for a selected animal, a fasting day only for one not selected,
  V and Gy with a medicine note (EVE-01..EVE-05). Automatic fasting days at the close of a finalized
  list, recomputed when an admin changes a closed day, at a reclose (R-2) and when a lifecycle event
  is recorded later (R-1); a later death that would leave manual rows after it is refused with the
  list of those rows. Excel: the individual feeding log (one row per day and recipient, SUM per unit,
  never pieces with grams, D-30; Egyéb 1–5 with their names) and the eating pattern (days across,
  colours, V and Gy, the medicine note under its day, the dead struck through).
- Trial import file for the customer (VIZ-24): `npx tsx scripts/zims-trial-file.ts --pool <name>
  --date <day> --measured-by "<name in their ZIMS>"`; the real name is an argument, never stored.

The journal job runs once a minute inside the server (`src/instrumentation.ts`); `JOURNAL_JOB=off`
switches it off for an extra replica.
